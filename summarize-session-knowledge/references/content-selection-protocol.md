# 内容筛选、去重与隔离协议

本协议用于把会话片段转化为稳定知识，而不是把消息按顺序压缩。整理过程中执行，内部记录默认不写入成品。

## 1. 候选内容分类

| 类型 | 识别方式 | 默认处理 |
|---|---|---|
| 通用知识 | 脱离当前项目仍成立的概念、机制、方法 | 保留为正文主干 |
| 项目事实 | 只对特定仓库、版本、业务或环境成立 | 项目型文档保留；通用文档移入示例或删除 |
| 教学示例 | 用具体数据或代码解释抽象知识 | 保留少量，优先选一个贯穿示例 |
| 决策与约定 | 团队选择、架构取舍、流程约定 | 说明适用条件，不写成普遍规律 |
| 故障经验 | 现象、根因、修复、验证、预防 | 重构为复盘，不保留聊天时间线噪声 |
| 操作步骤 | 命令、配置、迁移或人工流程 | 增加前置条件、验证、风险和恢复方式 |
| 不确定信息 | 缺少证据、存在冲突或依赖环境 | 标记待确认、经验判断或证据边界 |
| 重复内容 | 含义相同，仅措辞或例子不同 | 合并到同一规范知识点 |
| 对话元文本 | 代理思考、工具过程、交付话术 | 删除，不进入正文 |
| 任务状态 | “接下来”“当前下一步”“已读取”等现场状态 | 删除；若是可复用流程则改写为一般步骤 |

## 2. 规范知识点台账

先在内部建立台账：

| 字段 | 含义 |
|---|---|
| ID | 临时 `K-nnn`，只用于整理 |
| 规范名称 | 不依赖具体问法的概念名称 |
| 一句话定义 | 该知识点最小稳定含义 |
| 来源 | 出现在哪些会话片段或材料 |
| 新增信息 | 后续片段真正增加的边界、例子、反例或纠正 |
| 类型 | 通用知识、项目事实、示例、决策等 |
| 前置知识 | 阅读它前需要先理解什么 |
| 归属主题 | 最终放入哪个章节或文件 |
| 处理 | 保留、合并、泛化、移动、标记待确认或删除 |

同一知识点多次出现时，把来源和新增信息并入原记录，不新建重复 ID。

## 3. 判断“重复”还是“相关”

### 应合并

同时满足以下条件时视为同一知识点：

1. 回答的是同一个核心问题；
2. 输入、输出、条件和适用范围基本相同；
3. 删除其中一个解释不会损失独立概念；
4. 差异只是措辞、代码变量名、业务对象或例子。

例如：

- “`v-model` 同步表单值”和“选择后字段自动更新”属于同一机制；
- “终止操作触发 Stream”与“`toList()` 让流水线执行”应并入惰性执行及终止操作的解释。

### 不应合并

出现以下任一情况时保持独立：

- 名称相似但语义不同，如 Stream 的 `map` 与 `Map<K,V>`；
- 一个是机制，一个是具体 API；
- 一个是通用规律，一个是项目约定；
- 条件或副作用不同，如 `git fetch` 与 `git pull`；
- 一个是正常流程，一个是异常恢复流程；
- 合并后会隐藏重要边界或风险。

相关但不同的概念可以放在相邻章节或“易混概念”表中。

## 4. 一个概念只讲一次

每个规范知识点选择一个“主解释位置”，该位置可以包含：

- 是什么；
- 为什么；
- 如何工作；
- 输入与输出；
- 适用条件；
- 一个主要示例；
- 易错点。

其他章节只能：

- 用一句话引用；
- 补充新的边界或反例；
- 在速查表中压缩；
- 在综合示例中实际使用。

不得在“核心知识”“完整流程”“技术点汇总”“最终总结”中四次完整复述同一概念。最终总结只留下记忆钩子。

## 5. 项目耦合三级模型

### 通用层

在其他项目和场景中仍成立。正文优先保留。

示例：

> `git cherry-pick` 将指定提交引入的差异应用到当前分支，并创建新的提交。

### 示例层

用于让抽象知识可观察。示例可以来自项目，但需满足：

- 读者无需认识业务名词；
- 示例中的关键数据足以理解；
- 明确它只是例子，不代表标准库或通用要求；
- 能用简单对象说明时，不保留冗长业务字段。

### 项目事实层

只能描述当前项目或代码基线，例如接口路径、表名、角色、提交哈希和状态值。处理规则：

- 项目知识说明或复盘中可保留；
- 在章节标题或范围说明中标记“当前实现”“项目约定”；
- 给出必要的一手定位和时效边界；
- 不将其改写为“所有项目都应该如此”。

## 6. 泛化项目示例

按以下顺序处理具体细节：

1. 判断细节是否承载知识；
2. 不承载知识则删除；
3. 只承载结构时改成中性名称；
4. 承载真实边界时作为项目示例保留；
5. 承载复盘证据时放入项目事实层。

可泛化：

```text
DailyCostPoint -> Order / Product / Number
A01_F01 -> category_region
绝对路径 -> <project-root>/src/...
具体 commit -> <feature-commit>
```

不应泛化掉：

- 冲突发生在哪个有效实现节点；
- 某条业务规则只在特定版本存在；
- 复现问题所需的准确接口、版本或配置。

## 7. 处理纠正与冲突

会话后文纠正前文时：

1. 不同时保留两个互相矛盾的结论；
2. 采用最后一个有证据支持的结论；
3. 若旧说法是常见误区，可放入“误区”并明确为何错误；
4. 如果无法判断谁正确，标记待确认并写出缺少的证据；
5. 不把“用户坚持”本身当成技术证据。

“最佳实践”“一定”“只能”等强结论必须核验适用条件。团队约定改写为：

> 在满足……条件时，可以采用……；若目标是……，另一种常见选择是……。

## 8. 多主题隔离决策

先为候选知识建立主题簇，再判断输出形态。

### 保留在同一文件

- 主题存在明确前置关系；
- 可以由一条主线串联；
- 每个子主题较短；
- 综合示例需要同时使用它们。

### 拆成多个文件

- 技术领域不同且没有前置依赖；
- 每个主题都有自己的术语、流程和复习目标；
- 任一主题可独立形成完整文档；
- 合并后标题层级超过三到四层，或大量使用“另外”；
- 读者可能只需要其中一个主题。

拆分结果：

```text
<知识集名称>/
├── README.md             # 总地图、阅读顺序、文件索引
├── <主题一>.md
├── <主题二>.md
└── <主题三>.md
```

公共知识选择一个权威文件，其他文件用相对链接引用。不要复制整段。

## 9. 对话元文本门禁

正文生成后搜索以下信号，并逐条判断删除或改写：

```text
The user wants me
Wait
thinking
深度思考
用户希望我
用户要求我
让我先
我接下来
我无法创建文件
请复制以下内容
工具调用
权限模式
记忆中
当前上下文
```

还要检查：

- 是否出现角色自述“作为 AI”；
- 是否记录读取文件、调用 agent、进入计划模式的过程；
- 是否把完成报告放进学习正文；
- 是否有用于包裹整篇文档的多余代码围栏；
- 是否有“上文”“刚才”“这个回答”等失去上下文的指代；
- 是否意外保留用户隐私、凭据或本机绝对路径。

关键词可能出现在反例或本协议自身，不能只做机械删除；判断其在成品中是否承担知识作用。

## 10. Markdown 完整性检查

交付前确认：

- 只有一个一级标题，知识集索引除外；
- 标题层级不跳级；
- 每个代码围栏成对闭合并标明合适语言；
- 表格列数一致；
- 相对链接指向真实文件；
- 没有整篇文档嵌套在另一个代码围栏中；
- 没有空章节和纯占位符；
- 示例代码在语法和上下文上自洽；
- 路径、命令和版本仅在必要时保留。

## 11. 完整性核对

把最终章节反向映射到候选知识台账：

- 每个保留的 `K-nnn` 都有落点；
- 每个删除项都有“重复、元文本、无关、不可核验或被替代”的理由；
- 每个章节至少对应一个真实候选知识点；
- 不为填模板新增会话中不存在、也未核验的知识；
- 用户明确要求的重点没有在泛化过程中被抹去。
